# `sodilaud` command-line tool

Roadmap item 8. `sodilaud notes.md [more.md ...]` opens the files in the running Sodilaud main
window, starting Sodilaud if needed, and returns at once.

## Decisions (2026-10-06)

- **Fire-and-forget only.** No `--wait` and no new IPC socket. `--wait` (block until the files
  are closed, for `$EDITOR` and `git commit`) is what makes VS Code and Zed run their own IPC; it
  moves to Later in the roadmap.
- **macOS and Linux.** Windows is not supported: the menu item is hidden there and the command
  refuses with a message.
- **Installed to `~/.local/bin/sodilaud`**, with no administrator prompt. When `~/.local/bin` is
  not on the user's PATH, the result says how to add it. The same menu item removes it.
- **A script, not a symbolic link.** On macOS a link to the binary inside the bundle would start
  a second Sodilaud process instead of going through Launch Services to the running one. A script
  also resolves paths and creates missing files before the app sees them.
- **Never clobber.** A `~/.local/bin/sodilaud` without our marker line is reported and left alone,
  on install and on remove.
- **Dev builds on macOS are refused.** A `tauri dev` binary is not inside an `.app` bundle, so
  `open -a` has nothing to open, and running the binary directly would start a second instance
  (macOS has no single-instance plugin). The dialog says to install from Sodilaud.app. A copy
  running from App Translocation (not yet moved out of Downloads) is refused the same way,
  because that path vanishes. Linux dev builds work: the single-instance handoff covers them.

## The script

POSIX `sh`, generated by `src-tauri/src/cli.rs` and written atomically (temporary file in the
same folder, mode 0755, rename). The second line is the marker:

```sh
# sodilaud-cli: installed by Sodilaud. Update or remove it from the Sodilaud menu (Command Line Tool).
```

For each argument, before anything is opened:

1. `-h` / `--help` prints usage; `--` ends options; any other `-x` is an error (exit 2). No
   arguments prints usage to stderr (exit 2).
2. A relative path is joined to `$PWD`, the terminal's working directory.
3. The name must end in `.md`, `.markdown` or `.txt` (any case), the extensions the main window
   opens; otherwise exit 1 with a message on stderr.
4. A folder is refused. A missing file's parent folder must exist; parents are never created.

Only when every argument passed are missing files created empty (`>>`, which never truncates),
then the app is launched with the absolute paths:

- **macOS:** `exec open -a '<Sodilaud.app>' <paths>`. Launch Services starts Sodilaud or
  activates it, and delivers the files as `RunEvent::Opened`, the Finder "Open With" path. The
  bundle path is baked in at install time from `current_exe()` (`.../X.app/Contents/MacOS/bin`).
  If the bundle is gone, the script says to reinstall.
- **Linux:** the executable baked in at install time (`$APPIMAGE` when set, as for MCP), run
  under `setsid` (or `nohup` when `setsid` is missing) in the background with stdio on
  `/dev/null`. A running instance gets the paths through `tauri-plugin-single-instance`; a new
  one opens them at startup. Either way the terminal returns at once.

Both routes end in `files::open_from_system`, so grants, recents, the document registry and
outside-edit merging apply as for Finder.

## Install and remove (`cli.rs`)

- `script(&Target)` builds the text; `Target::App(bundle)` on macOS, `Target::Executable(path)`
  on Linux. Baked paths are single-quoted for the shell.
- `state(path, script)` is `Missing`, `Current` (byte-identical), `Outdated` (ours, different:
  another copy or version of Sodilaud) or `Foreign`. A symbolic link or unreadable file there is
  `Foreign`.
- `install` refuses `Foreign`, creates `~/.local/bin` if needed and writes the script. Running it
  again is a no-op. `remove` deletes only our script and refuses `Foreign`.
- `on_path(dir, PATH)` compares entries with `std::env::split_paths`. The app's own `PATH` is
  not enough: a Finder- or desktop-launched app inherits a minimal one. The check also asks the
  login shell (`$SHELL -ilc`, 3 s limit, stdin closed) and accepts either.
- `path_hint(shell)` names the profile to edit: `~/.zshrc` for zsh, `~/.bashrc` for bash
  (`~/.bash_profile` on macOS), `fish_add_path` for fish, a generic line otherwise.

## UI

One item, **Command Line Tool...**, which opens a native dialog that fits the state:

- missing: what it installs and where, with **Install** / **Cancel**, then the result (and the
  PATH hint when needed);
- current: where it is, with **Remove** / **Close**;
- outdated: **Update** / **Remove** / **Close**;
- foreign, or an unsupported build: an explanation and **OK**.

It lives in the native application menu on macOS (after About) and in the in-page **Sodilaud
menu** of the main window on macOS and Linux (in the Files section), hidden on Windows. Both
call the same Rust code (`cli_tool_offer`, granted to the main window only). The state and PATH
checks run off the main thread; the dialogs run on it.

## Tests

- Rust unit tests: script text (marker, quoting, launch line per target), bundle detection from
  an executable path, state detection, install and remove idempotency and the foreign-file
  refusal in a temporary home, `on_path`, and the PATH hint per shell.
- A Rust test runs the generated script with `sh` against a fake executable that records its
  arguments: relative paths become absolute, missing files are created, other extensions and
  missing parent folders are refused with nothing created or launched. It runs on macOS and
  Linux CI.
- JS: the Sodilaud menu item invokes `cli_tool_offer` and is hidden on Windows; the command is
  declared, permissioned and granted to the main window only.
